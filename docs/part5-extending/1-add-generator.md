# 1. 加一个生成器

**场景**：你想让 polyforge 生成一种新产物（如 OpenAPI 文档、PlantUML 图、前端表单代码）。

## 步骤

### 0. 决定它是不是一个新 target

polyforge 的生成按 **target** 组织：`--target=frontend` / `backend` / `db` / `openapi` / `all`。每个 target 是**独立完整的生成器集合**，`gen` 只是把它们依次跑。

新生成器落进两种形态之一：

| 形态 | 例子 | 做法 |
|---|---|---|
| **加进已有 target** | 给 backend 加一个 Assembler 生成器 | 在 `index.mjs` 的 `if (wantBackend)` 段里加一行，config 不用改 |
| **新建 target** | OpenAPI 导出、PlantUML 图 | 加 target 名到 `VALID_TARGETS`，加 `outputs.<新target>` 配置段，加 `wantXxx` 分支 |

下面按「新建 target」讲，因为它覆盖的改动最多。

### 1. 写生成器模块

在 `polyforge/generators/` 下新建目录与文件：

```js
// polyforge/generators/openapi/index.mjs
export function generateOpenApi(ir, outDir) {
  // 读 ir，往 outDir 写文件
}
```

**约定**（必须遵守）：

- 签名 `(ir, outDir)`——只读 IR，输出目录由参数给
- 自己 `mkdirSync(outDir, { recursive: true })`
- 产物首行带 `// AUTO-GENERATED by polyforge. DO NOT EDIT.`
- 不读源文件、不联网、不依赖外部状态

> 若产物是文本（SQL、Markdown），标记用对应注释符；
> 若是 JSON，则放在生成时而非文件头。

### 2. 加 target 名

`polyforge/index.mjs` 顶部：

```js
const VALID_TARGETS = ['all', 'frontend', 'backend', 'db', 'openapi']  // ← 加新 target
```

### 3. 接线到入口

`polyforge/index.mjs` 的 gen 分支：

```js
import { generateOpenApi } from './generators/openapi/index.mjs'

// gen 分支里
const wantOpenapi = target === 'all' || target === 'openapi'

if (wantOpenapi && out.openapi) {
  console.log('')
  console.log('[polyforge] 生成 OpenAPI...')
  generateOpenApi(ir, out.openapi)
}
```

### 4. 加配置字段

`polyforge/config.mjs` 里解析新的输出路径（`outputs.openapi` 是一个目录字符串，不是对象——除非它自己也分多个产物）：

```js
openapi: userConfig.outputs?.openapi
  ? resolve(cwd, userConfig.outputs.openapi)
  : null,
```

### 5. 写测试

在 `polyforge/tests/cases/` 加一个用例，验证生成器在正常/异常模型下的行为。`tests/gen-smoke.mjs` 里的正向 case 也可以复用——它跑 `gen` 后检查产物特征。

### 6. 更新文档

- [产物](../part3-usage/3-outputs.md) 的表里加一行
- [命令行](../part3-usage/2-cli.md) 的 `--target` 说明里加新值
- [配置](../part3-usage/1-config.md) 的 `outputs` 表里加新段

## 约束

| 约束 | 原因 |
|---|---|
| 只读 IR | 生成器不解析 YAML、不做校验，职责单一 |
| 输出目录由参数给 | 不硬编码路径，路径由配置决定 |
| 无副作用 | 纯函数，可重复执行、可测试 |
| 不 import 其他生成器 | 生成器之间不互相依赖 |

## 参考实现

| 生成器 | 适合看什么 |
|---|---|
| `generators/java/entity.mjs` | 最简：IR → 一组文件 |
| `generators/frontend/types.mjs` | 跨文件引用（import 处理） |
| `generators/frontend/requestMap.mjs` | 按方法分组、逻辑键 |
| `generators/java/service.mjs` | 手写保护（骨架刷新/保护） |

## 不产生 manifest

`gen` **不写 manifest.json**——`manifest.json` 已于 2026-10-20 删除，原 `verify` 命令由 `gen && git diff --exit-code` 替代。

新生成器无需考虑 manifest 或 verify。原因见 [BASELINES.md](../BASELINES.md#manifestjson-为什么删了)。

## 常见坑

- **类型映射漏项**：新类型出现时，生成器要有对应分支，否则抛错（fail fast 是有意的）。
- **跨端一致性**：新产物若涉及 id、日期、枚举，参照[类型系统](../part2-model-spec/8-type-system.md)的映射表。
- **别忘 import 收集**：生成 TS/Java 时，用到跨文件类型要收集并生成 import。
