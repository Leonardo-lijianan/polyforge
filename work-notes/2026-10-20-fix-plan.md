## 阶段五：版本策略与配置 schema 版本（2026-10-20 追加）

### 背景

F4 把 `basePackage` 从「可选但没人用」变成「必填」，F5 改了生成器源文件名。按 semver 严格语义这是 breaking，但当时只升到 `0.3.0`（minor）。用户指出应该用 `major.minor.hotfix` 严格语义，有 breaking 就动 major。

### 决策

1. **polyforge 包版本**：`major.minor.hotfix`
   - major：breaking（配置字段收紧/删除、CLI 语义变化、产物结构变化、生成器源文件改名、校验规则收紧、新增硬依赖）
   - minor：新功能且向后兼容（新增可选字段、新增 CLI 命令、新增 warning 规则）
   - hotfix：纯修复（生成器 bug、校验误报、测试脚本 bug、文档修正）
2. **配置 schemaVersion**：`major.minor`（两段，**必须带引号**）
   - 与包版本格式不同，因为配置格式不需要 hotfix 粒度
   - 只在配置格式 breaking 时递增 major；新增可选字段递增 minor
   - 兼容判定只看 major：polyforge `1.x.y` 接受 `1.*`
   - **缺失即 error**，不给默认值——避免重蹈 `basePackage`「默认值即测试值」的覆辙
3. **关联规则**：schemaVersion 只跟配置格式走。工具 breaking 但配置格式没变，只动 major 不动 schemaVersion。

### 落地

- 新增 `docs/VERSIONING.md`（权威规范，含判定规则、边界判断三问、发布流程、兼容表、历史记录）
- `config.mjs` 新增 `SUPPORTED_SCHEMA_MAJOR = 1` / `SUPPORTED_SCHEMA_VERSION = '1.0'`
- `config.mjs` 的 `loadConfig` 增加 schemaVersion 必填 + 格式 + major 兼容校验
  - 兼容 YAML 裸数字陷阱（`1.0` 被解析成 `1`），兜底当作 `'1.0'` 处理，但文档推荐始终带引号
- `package.json` 版本：`0.3.0` → `1.0.0`
- 两个消费方配置（`we-engine-server` / `we-engine-client`）加 `schemaVersion: '1.0'`
- `tests/gen-smoke.mjs` 的 CONFIG 加 `schemaVersion: '1.0'`，并补三个负向 case：缺失、major 不匹配、裸数字兜底
- `docs/README.md` 挂 VERSIONING 链接，状态行更新为 2026-10-20
- `docs/part3-usage/1-config.md` 新增 `schemaVersion（必填）` 小节

## 阶段六：契约缓存重构（2026-10-20 追加）

### 问题

原设计把契约 clone 缓存放 `<projectRoot>/.polyforge/cache/`：

1. **归属错位**：契约仓库是跨项目共享的外部资源，放某个项目目录下等于说「这份缓存属于 server」，但它不属于任何项目
2. **重复**：client 和 server 各 clone 一份，靠 `rebuild.ps1` 手工设 `POLYFORGE_CACHE` 才能共用
3. **缓存没省下网络**：每次 gen 都 `git pull`，分支没变也得 fetch 一遍才知道。client + server 各跑一次 = 两次无谓传输

### 修法

**1. 默认缓存位置改到系统临时目录，跨项目共享**

```
<tmp>/polyforge-cache-<user>/<repo-name>-<url-hash>-<ref>/
```

- `config.mjs` 用 `os.tmpdir()` + `os.userInfo().username` 派生默认值
- 目录名加 URL 短哈希（sha1 前 8 位）：不同 org 的同名仓库不撞车
- `POLYFORGE_CACHE` 仍可覆盖（CI 持久化目录用）

**2. 更新策略：先探测远程版本，同版本跳过网络传输**

| ref 类型 | 行为 |
|---|---|
| branch | `ls-remote` 取远程 HEAD sha，与本地 HEAD 比较；相同跳过，不同才 `fetch` + `reset --hard` |
| tag / commit | 不可变。本地已有该 commit 对象即用，没有才 `fetch` |

`reset --hard` 而非 `pull --ff-only`：契约 clone 是只读工作副本，不该有本地改动，reset 保证与远程完全一致，且能修复被手动改坏的缓存。

**3. 短 sha 规范化**

commit 类型下用户可能配短 sha，与完整 HEAD 直接比较永远不等，会每次都走 checkout。用 `rev-parse --verify` 规范化后再比。

### 快照为什么不动

缓存是契约数据（可重新 clone，与项目无关）→ 移出项目合理。
快照是生成历史（记录「本消费方上次 gen 到哪个契约版本」）→ 是破坏性变更的确认点。

若快照也默认全局共享：server 先 gen 接受某破坏性变更并更新快照，client 下次 gen 时该变更已被「接受」过，静默通过。这比缓存重复危险。所以快照维持 per-project 默认 + `rebuild.ps1` 显式设 `POLYFORGE_SNAPSHOT` 做工作区级共享。

### 落地文件

## 阶段七：删除 manifest.json 与 verify（2026-10-20 追加）

### 判断

`manifest.json` 记生成物 MD5，`verify` 读它检测「生成物被手改」。这个检测价值有限：

1. `gen` 会清空整个 `generated/` 重建，手改本来就没有持久意义
2. 「契约变了忘记 gen」用 `polyforge gen && git diff --exit-code` 检测更通用，不需要专有概念
3. `--strict` 的孤儿检测同样多余——目录每次重建，不可能有孤儿
4. manifest 每次全量重写，提交到 git 是无意义 hash 噪音

结论：manifest 是「自检工具的输出」，不是状态；两个必须入库的基线已经够用，第三个是纯负担。
